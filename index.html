The brief

Design and deploy a scalable, cloud-native Python web application with a dual-cloud architecture targeting both AWS and Microsoft Azure. Docker containers orchestrated on Kubernetes (EKS / AKS), managed persistent data via PostgreSQL, and secure public routing via Ingress Controllers — with the entire multi-cloud infrastructure provisioned and replicated using Terraform.

Rather than one shared live database, each cloud runs its own complete, independent stack — same app image, same schema, own database, own Ingress. That keeps the architecture honest about what "multi-cloud" actually costs to run, without the added complexity of cross-cloud data replication.

AWS VPC (10.0.0.0/16) ├─ public + private subnets, NAT ├─ EKS cluster (ogplatform-eks) │ └─ 3× t3.micro nodes ├─ RDS PostgreSQL 16.9 ├─ ECR (ogplatform-app:v1) └─ ALB via aws-load-balancer- -controller → public URL
AZURE Resource group (ogplatform-rg) ├─ VNet (10.1.0.0/16) + subnet ├─ AKS cluster (ogplatform-aks) │ └─ 2× Standard_D2s_v7 nodes ├─ PostgreSQL Flexible Server 16 ├─ ACR (ogplatform-app:v1) └─ NGINX Ingress → public IP

The application (built once, deployed twice)

A small FastAPI service simulating an oil & gas sensor-monitoring backend: /health for Kubernetes probes, /readings as a JSON API, /dashboard as a styled HTML view for screenshots and demos, colored by which cloud it's running on via a CLOUD_PROVIDER env var. Identical code and image on both clouds — only the database connection string and that one env var differ.

import os
from datetime import datetime
from fastapi import FastAPI
from fastapi.responses import HTMLResponse
from sqlalchemy import create_engine, text

app = FastAPI(title="O&G Multicloud App")

DB_URL = os.getenv("DATABASE_URL", "postgresql://user:pass@localhost:5432/appdb")
CLOUD = os.getenv("CLOUD_PROVIDER", "unknown")
engine = create_engine(DB_URL, pool_pre_ping=True)

@app.get("/health")
def health():
    return {"status": "ok", "time": datetime.utcnow().isoformat()}

@app.get("/readings")
def readings():
    with engine.connect() as conn:
        rows = conn.execute(text("SELECT id, sensor_id, value, unit, recorded_at FROM readings ORDER BY recorded_at DESC LIMIT 20")).mappings().all()
        return {"count": len(rows), "readings": [dict(r) for r in rows]}

@app.get("/")
def root():
    return {"app": "O&G Multicloud Platform", "cloud": CLOUD}

@app.get("/dashboard", response_class=HTMLResponse)

app/seed.py
import os
import random
from datetime import datetime, timedelta
from sqlalchemy import create_engine, text

DB_URL = os.getenv("DATABASE_URL", "postgresql://user:pass@localhost:5432/appdb")
engine = create_engine(DB_URL)

SENSORS = [
    ("PRESS-01", "psi", 1400, 1600),
    ("TEMP-02", "°C", 60, 95),
    ("FLOW-03", "bbl/hr", 200, 450),
    ("VIB-04", "mm/s", 0.5, 4.0),
]

with engine.begin() as conn:
    conn.execute(text("""
        CREATE TABLE IF NOT EXISTS readings (
            id SERIAL PRIMARY KEY,
            sensor_id VARCHAR(20),
            value NUMERIC,
            unit VARCHAR(10),
            recorded_at TIMESTAMP
        )
    """))
    now = datetime.utcnow()
    for i in range(20):
        sensor_id, unit, low, high = SENSORS[i % len(SENSORS)]
        value = round(random.uniform(low, high), 2)
        conn.execute(
            text("INSERT INTO readings (sensor_id, value, unit, recorded_at) VALUES (:s, :v, :u, :t)"),
            {"s": sensor_id, "v": value, "u": unit, "t": now - timedelta(minutes=i*5)}
        )
print("Seeded 20 readings.")

09 The pod-scheduling wall

Hit — Pod stuck Pending: "0/1 nodes are available: 1 Too many pods." A t3.micro node supports very few pods once system daemonsets (kube-proxy, VPC CNI, CoreDNS) are counted. Scaled the node group 1 → 2, then hit the same wall again once the AWS Load Balancer Controller's 2 pods landed — scaled to 3 nodes total. 
aws eks update-nodegroup-config --cluster-name ogplatform-eks --region eu-west-1 \
  --nodegroup-name <name> --scaling-config minSize=1,maxSize=3,desiredSize=3
Terraform's EKS module intentionally ignores desired_size changes after creation (assumes a cluster autoscaler owns scaling) — terraform plan reported "no changes" even after editing the file. Had to scale directly via the AWS CLI instead, and keep the .tf file's value in sync manually.

What actually broke, and why it's worth knowing

Neither cloud account behaved like a clean tutorial environment — both had real, undocumented restrictions that only surfaced by trying, reading the actual error, and querying the account's real capabilities instead of guessing.

Instance-type restrictions aren't always obvious

Both AWS (free-tier-only enforcement) and Azure (subscription-level allowed-VM-size lists) rejected instance sizes considered "standard" in every tutorial. The fix each time was querying the account's actual allowed list and quota, not assuming any size would work.

Region availability isn't uniform per-service

Azure PostgreSQL Flexible Server was blocked in a region where AKS itself worked fine. A service being available in a region doesn't mean every dependent service is.

Kubernetes auth defaults shift underneath you

A kubectl client too new for an older AWS CLI's auth output, and EKS's newer API-based access entries replacing the legacy aws-auth ConfigMap — both "correct" in isolation, silently incompatible together.

Small nodes hit pod-count ceilings fast

Free-tier-eligible instance types (t3.micro) support far fewer pods per node than their vCPU count suggests once system daemonsets are counted — a load balancer controller alone can tip a small cluster over the edge.

Infrastructure-as-code doesn't manage what you create by hand

Resources created outside Terraform (an eksctl-managed IAM role, a manually created ACR) don't show up in terraform destroy — and can silently block it. Everything not in state has to be tracked and removed manually.
